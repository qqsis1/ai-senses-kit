# 插件：同包合并可行，跨包聚合会死锁

这是在某个 Harness 的插件体系上实测出来的结论（含 bundle 所有权的具体报错），换平台思路相通。

## 一、两类"合并"

| 方式 | 做法 | 结果 |
|---|---|---|
| **同包合并** | 同一个包里多导出一个入口，patch 里插两行 | **可行**。例如：主体插件 + 设置子插件，共用一张卡片 |
| **跨包聚合** | 新建"聚合包"，依赖若干已装包，在 patch 里按模块名插行 | **会死锁** |

## 二、为什么跨包聚合会死锁

聚合包一旦依赖某个插件包，这个包就被两份 bundle 同时"拥有"：原 bundle 和聚合包。

- 想删原 bundle → `bundle-in-use`（聚合包还用它）；
- 想删聚合包 → 同样 `bundle-in-use`（原 bundle 还用它）；
- 更糟：先卸原包再装聚合包时，聚合包的依赖可能没被装进宿主目录，行在、模块找不到，插件直接"failed to import"。

**结论：绑定关系是"一个包一个 owner"，聚合不能靠依赖共享。**

## 三、真要合并怎么办

只有一条路：**把代码抄进一个包**。

- 对每个被合并的插件：复制 `lib/`（或入口文件）到新包的子目录，patch 用子路径 `newpack/old-name` 引入；
- 导出子插件的 locale/icon，否则设置页里没有名字、没有图标；
- 依赖（schema 库等）要么声明，要么内置 `node_modules`（引用方是链接目录时，宿主解析不到你包里的依赖）；
- 合并完重新装 bundle，**旧包先卸、新包再装**，别反过来。

## 四、动手前的检查清单

1. 每行插件的 `name` 能否从宿主目录解析到？
2. 配置是写在 bundle patch 里，还是用户 profile 的 override 里？后者只要行 id 不变就能继承；
3. 有没有同 id 的重复行（两份 patch 插同一个 id）——**重复会让管理器丢行**；
4. 回滚路径是否清楚：旧包能原样装回吗？tar.gz/版本号还在吗？

## 五、教训

- 别在别人的插件上打补丁当长期方案：**升级就没了**；
- 判断标准很朴素：**下次它更新，我会不会丢掉什么**；
- 管理界面显得太长，先看有没有"隐藏已归属组合包的行"这类开关——**有时候问题不在架构，在视图**。
